# 字段字典与口径

> 本文件是**人读的口径说明**。枚举的机器真源是飞书表里的 select options；`sync-dict` 会把线上最新选项回写成本文件的「当前枚举」章节。任何 Agent 判定字段前，先读本文件 + 跑一次 `ledger.mjs health`（后者会实时拉取选项）。

## 一、用户原始 8 个维度的落点

| 原始提法 | 落到的字段 | 口径修正 |
|---|---|---|
| 1. 复盘归属于哪个 BU | `归属BU` | 单选；跨多个 BU 选「跨BU/集团」，不确定选「待确认」 |
| 2. 具体是做什么的 | `项目标准名` + `复盘事项` | 拆成「检索主键」和「一句话说明」，避免把项目名写在长句里导致按项目召回失败 |
| 3. 国内还是海外 | `市场区域` | 单选，增加「全球」 |
| 4. 涉及哪些平台 | `涉及平台` | **多选**；平台名按标准写法，不写「JD」「抖店」等口语 |
| 5. 营销复盘还是日常工作复盘 | `复盘类型` | 单选；保持用户原始二分法，仅补「其他 / 待确认」 |
| 6. 复盘提交人 | `提交人` | 文本（外部人员也能填），与「产出方」分开 |
| 7. 内部还是外部复盘 | `复盘范围` | 明确定义为**复盘对象**：内部=我方团队/项目执行；外部=市场/竞品/行业/外部合作方 |
| 8. 自己团队还是服务商 | `产出方类型` + `产出方名称` | 拆成「类型」与「具体名称」（如 Digishare），便于按服务商聚合 |

另补 `资料归属`：登记「本人 / 他人 / 外部 / 未知」。因为存在大量不归属于用户的资料，台账只做只读引用，**不迁移、不编辑、不复制原文**。

## 二、A 组：检索主键（召回成败的关键）

| 字段 | 类型 | 口径 |
|---|---|---|
| 复盘标题 | text（主字段） | 原文标题；无标题时生成「项目标准名 + 覆盖周期 + 复盘」 |
| 项目标准名 | text | 归一化主键。查 `project-aliases.json` 把别名映射成标准名；新项目以此条写法为准并登记别名 |
| 项目别名 | text | 逗号分隔的已知别名/缩写/旧称 |
| 覆盖周期 | text | **复盘所覆盖的业务周期**，如「2026年8月」「2026Q3」「8/1-8/31」。用户问「8月复盘」时以这个字段为准 |
| 周期起 / 周期止 | datetime | 周期的结构化边界，供范围筛选。原文只有月份 → 取当月 1 日 / 月末 |
| 复盘提交日期 | datetime | **复盘成文或提交的日期**。与覆盖周期是两个概念，禁止混填 |
| 检索键 | text | 脚本生成，勿手改。拼接：项目标准名｜别名｜覆盖周期｜BU｜平台｜类型｜关键词 |

> 为什么要拆「覆盖周期」和「复盘提交日期」：8 月的复盘通常在 9 月初写成。只存一个日期，用户问「8 月复盘」就会命中错或漏掉。

## 三、B 组：分类标签

判定原则：**有明确依据才归类，没依据一律填「待确认」并勾「待人工确认」，不要猜**。所有 select 字段都带「待确认」兜底。

- `归属BU`：按复盘服务的业务单元归属，不是按提交人所在部门。
- `市场区域`：按复盘覆盖的市场判断；同一份复盘覆盖国内+海外 → 选「全球」。
- `涉及平台`：原文明确提到的渠道/平台才勾选；「全渠道」这类泛称记到 `备注`，不要把所有平台都勾上。
- `复盘类型`：以复盘主体判断。投放/活动/Campaign/内容/电商效果 → 营销复盘；流程、协作、例会、日常运营 → 日常工作复盘。
- `复盘范围`：见上表定义。服务商做的复盘若复盘的是我方项目，仍是「内部复盘」；「外部复盘」指的是复盘对象在外部。
- `产出方类型` / `产出方名称`：谁写的这份复盘。多个产出方 → 选「混合」，名称里都列出。

## 四、C 组：原文定位

- `载体类型`：决定用哪套读取流程，见 `source-readers.md`。
- `资料归属`：**只读元信息**，不改变任何原始文件的权限或位置。
- `原文链接` / `本地路径`：二选一或都填（例如既有在线版又有本地副本）。
- `可读状态`：Agent 实测能否读通。链接打不开就如实标「链接失效 / 需登录 / 需权限」，不要标「可直接读取」。
- `来源指纹`：脚本生成。规范化 URL（去 query、去末尾斜杠）后取 hash；本地文件用路径+文件名；纯文本用内容 hash。**同指纹只保留一条记录**。

## 五、D 组：内容沉淀（内容召回靠这一组）

| 字段 | 要求 |
|---|---|
| 一句话结论 | 原文的核心判断，一句话 |
| 核心策略 | **逐条编号分行**列出原文提到的策略/打法。回答「复盘里提到的策略是什么」时优先取此字段 |
| 关键数据 | 保留原始数字与单位，不换算、不四舍五入 |
| 内容摘要 | 200–500 字，结构：背景 / 动作 / 结果 / 结论 |
| 关键词 | 3–8 个，逗号分隔，优先用用户会说的词（项目名、月份、平台、品类） |
| 原文摘录 | 支撑结论的**原样摘录**，不改写。无依据时留空 |

> 沉淀到台账的原因：外部链接（腾讯文档 / HTML 报告）随时可能失效或需要登录。把一次解析的成果留在台账里，内容召回就不依赖链接永远可用。原文全文不入库，只入库结构化成果 + 链接。

## 六、E 组：运维与去重

- `登记来源`：登记该条的 Agent/会话标识（如 `WorkBuddy/主会话`）。多 Agent 共用时用于溯源与排查口径不一致。
- `登记时间` / `最后变更`：系统字段，只读。
- `解析状态`：已读全文 / 仅摘要 / 未读取 / 无法访问。内容召回时若状态非「已读全文」，回答要注明依据不足。
- `置信度`：0–1，Agent 对自动抽取结果的把握。< 0.7 必须勾「待人工确认」。
- `待人工确认`：人工审核闸。勾上的记录不影响检索，但回答时要提示「该条自动抽取结果待确认」。

## 七、归一化规则

1. **项目名**：先查 `project-aliases.json`，命中任一别名 → 写成标准名；未命中 → 保留原文作标准名，并把原文追加进别名表。
2. **月份**：`8月` / `2026年8月` / `2026-08` 统一在 `覆盖周期` 里写「2026年8月」，`周期起/止` 填 2026-08-01 / 2026-08-31；原文未给年份时按上下文推断，推断不了写「待确认」并勾人工确认，**禁止默认填当前年份**。
3. **平台**：小写/英文/缩写统一到标准选项（JD→京东，Douyin→抖音，Tmall→天猫，Amazon→亚马逊，Sam's→山姆）。
4. **select 未知值**：不要硬塞。落到「待确认」，把原值写进 `备注`，并交给 `sync-dict` 沉淀为候选值。

## 八、当前枚举

> 由 `sync-dict` 从线上字段实时生成。若此处与线上不一致，以线上为准并跑一次 `sync-dict` 刷新。

- 载体类型：飞书云文档、飞书多维表、腾讯文档、在线HTML报告、本地文件、纯文本段落、邮件、其他
- 市场区域：国内、海外、全球、待确认
- 解析状态：已读全文、仅摘要、未读取、无法访问
- 涉及平台：京东、天猫、山姆、抖音、小红书、亚马逊、独立站、线下门店、微信/公众号、B站、快手、其他、待确认
- 复盘类型：营销复盘、日常工作复盘、其他、待确认
- 归属BU：水健康/净水、个护、按摩、运动/Fitness、母婴、海外、跨BU/集团、其他、待确认
- 资料归属：本人、他人、外部、未知
- 产出方类型：自己团队、服务商、混合、其他、待确认
- 可读状态：可直接读取、需登录、需权限、链接失效、仅本地、待核验
- 复盘范围：内部复盘、外部复盘、内外部结合、待确认
